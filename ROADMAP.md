# Roadmap

This is a living, evidence-driven roadmap for `run-2026-11-25-001`. It records measurable milestones toward a `packages/`-based monorepo, reproducible checks, and runtime validation of the emulation stack. Status changes only when a result is backed by a linked log or source file.

## Evidence policy

- Verified: reproduced by the single tester and recorded in a log.
- Upstream-reported: inherited from the base project or its documentation, not reproduced in this run.
- Unknown or not verified: no evidence available yet. Do not infer success from absence of failures.
- Never claim 30 FPS, crash-free gameplay, or full-game completion without tester evidence.
- Only one tester runs builds, tests, and the game. Keep game paths, caches, and captures outside the repository.
- Outward GitHub actions are allowed only under `dorkyfolf`, never `callmeteus`.

Status values used below: `done`, `in progress`, `partial`, `blocked`, `unknown`, `not verified`, `pending`.

#### Verified runtime observation

Pointed at the interner `FUN_141adcc20` (RVA `0x1adcc20`), it captured 200 names, including a `decoration` call immediately before the crash and names such as `standard_rdp`, `im`, and `scaleform_shaders_*` (E18). This is an observation of the running title under the watch, not proof of a fix: the runtime remains unverified and no FPS or stable gameplay is claimed.

#### Runtime frontier

The original null dereference at `victory-image+0xb5a5f8` was eliminated by the opt-in presets compatibility shim, which redirects the title's internal `platform:/data/settings/presets.zmt` open to a `memory:` URI carrying a process-lifetime 160-byte blob (E21, E22). That redirect exposed a pool-size assert at `+0x247af2d` on the URI's declared size; Ghidra proved the condition `(uint64)(size - ptr + base) <= 0x1FFFFF`, and a runtime correction (`VICTORY_FIX_PRESETS_ASSERT=1`) rewrote the size so `rax` went from `0x2f20000` to `0x100000`, after which the assert stopped firing (E22). The remaining blocker appears only when the two mechanisms are combined: the run ends in `STATUS_SINGLE_STEP` (`0x80000004`) exceptions at `+0x28cd2a0` and reaches neither `XUserAddAsync` nor frame presented (E23). No FPS telemetry was observed, so no frame rate is claimed. No title patch was written to disk and no fake gameplay asset was created (E23).

#### Root cause and current state

The boot crash root cause is now identified as the in-box Windows 10 D3D12 runtime: it refuses the title's root signatures with flags `0xc00` or `0xc01` at `hr=0x80070057`, after which the title null-derefs at `victory-image+0xb5a5f8` (E24).
